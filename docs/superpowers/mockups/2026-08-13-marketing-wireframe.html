Marketing section — UI plan

Static wireframes for the planned Marketing section — spool returns, points, and website banners — rendered in the app’s own design tokens so they read as the real product. Every name shown (“Spool Points”, “spools”) is the seeded preset: it is config the owner can rename on day one, never hard-coded copy.

1 · Section landing

/marketing

A new top-level section, peer of Posts / Shop / Emails, with six subsections in the rail: Overview, Returns, Rewards, Customers, Banners, Discounts. The landing page is a workload router: four stat tiles that are links into the returns queue, the oldest open returns with their next action inline, the latest points activity, and a self-removing first-run checklist driven by real state.

2 · Returns queue

/marketing/returns

The hero surface. One list, grouped by stage in pipeline order, under a counted tab strip fed by a real counts sidecar on every response — no fake tab numbers. Each row carries the server-computed allowedActions, so it shows exactly one next-action button; schedule / collect / receive open in place, while Inspect always navigates to the detail form. Waiting time warns at 48h and escalates at 96h — colour plus text, never hover-only.

3 · Return detail — lifecycle & stage actions

/marketing/returns?id=ret_…

Request → schedule → pick up → receive → inspect → award, drawn as a five-dot stage path. The left panel always offers one primary next step for the current stage — here, the inspection form: staff type Received and Accepted, Rejected is derived (never typed, so the sum-mismatch error cannot exist), and one interpolated sentence (“5 accepted × 10 = 50 Spool Points…”) travels unchanged into the confirm dialog, the toast, the timeline and the email.

4 · Rewards — program editor

/marketing/rewards?id=prg_…

Nothing about the naming is fixed: program name, points labels and unit labels are form fields, not copy. The right-hand panel restates the rules in plain words and renders a sample email from the draft labels, so a rename is verified against the customer-facing artifact before it is saved. History keeps its old wording — a rename changes the future, never the past. Owner-only; writers see a read-only recap.

5 · Banners — editor with live preview

/marketing/banners?id=bnr_…

Banners are content + placement + window + priority. The enabled switch maps draft ↔ live; scheduled / ended are derived from the window at read time by one shared pure function (the same logic the public endpoint runs), and the editor says the result in a sentence. There is no delete — archive is a separate, confirmed action. The preview repaints from current values in admin tokens.

Drawn elsewhere, not forgotten

  • Customers — balance lookup with guests as first-class citizens, an append-only day-grouped ledger (“120 → 180” from stored balance-after), and the owner-only adjust-balance dialog.
  • Rewards settings panel — owner-only block at the top of Rewards (cross-program labels, redemption rate, default program); it earns no seventh nav item.
  • Discounts — ships as an honest static placeholder: no dead buttons, no fetches; the API lands first.
  • Dialogs — schedule pickup, reject/cancel reasons and confirmations become bottom sheets at ≤640 px (same component, same focus trap).
  • Error treatments — every 409 carries the re-read entity, so conflicts auto-heal: the true stage re-renders, a toast says so, and mid-edit inputs are preserved behind a notice instead of wiped.
  • States — delayed skeletons, real zeros on fresh installs, per-region errors with Retry; a stats failure never blanks a panel.
